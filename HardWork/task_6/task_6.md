## 2. Первая задача: расчёт энергии по получасовкам

### 2.1. Словесный контракт

Функция получает показания средней мощности за получасовые интервалы и
возвращает рассчитанную энергию в кВт·ч.

Для каждого принятого интервала:

```text
энергия = средняя мощность × 0,5 часа
```

Одинаковые значения мощности с разными временными метками являются разными
интервалами и учитываются оба. Точный повтор одной записи идемпотентен и
учитывается один раз. Разные значения для одной временной метки образуют
конфликт: такая получасовка исключается из суммы, а результат маркируется как
недостоверный.

### 2.2. Первый проход без предварительного дробления

Первый тест определил только результат для пустого набора. Реализация была
фейковой:

```python
def calculate_energy(readings):
    return EnergyResult(energy_kwh=0.0, is_reliable=True)
```

После зелёного теста был создан коммит. Затем отдельным тестом добавлена одна
получасовка мощностью 4 кВт. Тест ожидал 2 кВт·ч и первоначально был красным.
Минимальное обобщение заменило константу суммированием:

```python
energy_kwh = sum(reading.average_kw * 0.5 for reading in readings)
```

Следующий тест закрепил предметное правило: одинаковая мощность в разные
моменты времени не является дублем. Этот тест сразу оказался зелёным, потому
что текущее суммирование уже удовлетворяло правилу.

Далее появился тест точного повтора. Для его прохождения была введена
дедупликация по временной метке:

```python
unique_by_start = {
    reading.start: reading.average_kw for reading in readings
}
```

На этом этапе все существовавшие тесты проходили, поэтому изменение было
закоммичено. Однако реализация неявно ввела новое правило: при разных значениях
для одного времени побеждает запись, которая встретилась последней.

Тест всех перестановок набора `4/9/6 кВт` обнаружил зависимость результата от
порядка входных данных. Этот шаг оказался неудачным, но размер изменения был
мал: между рабочим состоянием и ошибкой находился один новый тест. Вместо
попытки исправлять словарь дополнительными условиями данные были сгруппированы
в множества вариантов по времени. Конфликтующие группы исключаются целиком.

### 2.4. Инспекция первой задачи

После первого прохода видно, что последние изменения можно было сделать ещё
меньше.

Тест конфликта одновременно проверяет четыре свойства:

1. конфликт обнаруживается;
2. конфликтующая получасовка исключается;
3. результат становится недостоверным;
4. поведение не зависит от порядка записей.

Из-за этого последний шаг первой задачи получился самым большим: тест вырос на
20 строк, а реализация изменилась на 21 строку. Более мелкая последовательность
могла выглядеть так:

1. один конфликт помечает результат как недостоверный;
2. конфликтующая группа не входит в сумму;
3. точный повтор остаётся допустимым;
4. результат одинаков для всех перестановок.

Кроме того, типы `HalfHourReading` и `EnergyResult` были введены вместе с
первым тестом. Их можно было добавить отдельным подготовительным коммитом без
изменения поведения.

Тест одинаковой мощности в разные моменты сразу прошёл. Это допустимо как
закрепление уже существующего поведения, но он не доказал свою чувствительность
через стадию RED. При строгом TDD полезно временно исказить реализацию и
проверить, что такой тест действительно обнаружит ошибку дедупликации по
значению.

## 3. Вторая задача: обнаружение провала напряжения

### 3.1. Словесный контракт

Функция получает напряжения по фазам и номинальное напряжение. Провалом
считается значение строго ниже 70% номинала, то есть снижение более чем на 30%.
Значение ровно на границе 70% провалом не является.

Каждая фаза проверяется независимо. Отсутствующее или неконечное измерение не
останавливает обработку остальных фаз, а помещается в `invalid_phases`.
Наличие таких фаз делает результат недостоверным.

### 3.2. Второй проход после инспекции

После инспекции первой задачи правила второй задачи добавлялись по одному:

1. нормальное напряжение не образует провал;
2. одна фаза ниже порога образует провал;
3. значение ровно 70% допустимо;
4. каждая фаза проверяется независимо;
5. отсутствие измерения маркируется отдельно;
6. `NaN` также считается недостоверным измерением.

Первый тест снова прошёл на фейковой реализации:

```python
def detect_voltage_sags(phase_voltages, nominal_voltage):
    return VoltageSagResult(dropped_phases=())
```

После появления теста пониженного напряжения была написана первая настоящая
проверка. В ней сознательно использовалось недостаточно уточнённое сравнение:

```python
voltage <= nominal_voltage * 0.70
```

Все имевшиеся тесты были зелёными, поэтому состояние было сохранено. Следующий
маленький тест на точной границе немедленно показал ошибку: формулировка
«провал более чем на 30%» требует строгого оператора `<`. Исправление состояло
в замене одного символа.

Отсутствующее значение и `NaN` тоже вводились раздельными тестами. Поэтому при
появлении каждого красного состояния причина была однозначна и не требовала
одновременного анализа нескольких правил.

| `42b6321` | Определено нормальное состояние и добавлен фейк. |

| `b5ba20e` | Уточнено поведение на точной границе 30%. |

### 3.4. Инспекция второй задачи

Во втором проходе локализация ошибок стала проще. Самое маленькое исправление —
замена `<=` на `<`: одна строка реализации и один отдельный тест предметной
границы.

Крупнейшее изменение реализации потребовалось при добавлении отсутствующего
измерения: генератор был преобразован в явный цикл. Это структурное изменение
можно было предварительно выполнить отдельным рефакторингом при зелёных тестах,
а уже следующим коммитом добавить `invalid_phases`. Тогда изменение поведения
занимало бы ещё меньше строк.

Тест нескольких фаз сразу оказался зелёным. Как и в первой задаче, это
характеризационный тест: он закрепляет существующее поведение, но не двигает
реализацию через RED. Такие тесты полезны, однако их назначение следует отличать
от тестов, которые непосредственно ведут разработку.

## 4. Сравнение двух проходов

В первой задаче я двигался привычным способом и в конце объединил в одном тесте
несколько требований. Это привело к изменению примерно сорока строк теста и
реализации за один шаг.

После инспекции во второй задаче каждое предметное правило получило отдельный
тест. Неудачная трактовка границы была исправлена заменой одного оператора.
Отсутствующее значение и `NaN` не объединялись в один общий сценарий.

Таким образом, практически удобный размер шага для этих задач составил:

- один новый пример поведения;
- один тест размером примерно 5–10 строк;
- изменение реализации от 1 до 12 строк;
- полный прогон тестов;
- отдельный зелёный коммит.

Стремиться к минимальному числу изменённых строк само по себе не требуется.
Критерий хорошего шага другой: при падении теста должна оставаться одна
очевидная гипотеза о причине.

## 5. Коммиты и применение в рабочем процессе

В обычной экспериментальной работе с ML/ASR коммиты часто делаются после
завершения целой клетки ноутбука, эксперимента или заметного блока логики. В
backend-разработке изменения иногда объединяют модель, сериализатор, API и тесты
одним коммитом. Это создаёт слишком большое расстояние между зелёными точками.

Из выполненной практики в настоящую работу можно перенести следующие правила:

1. Перед изменением запускать связанный набор тестов и фиксировать зелёную
   исходную точку.
2. Отделять подготовительный рефакторинг от изменения предметного поведения.
3. Добавлять по одному предметному правилу или одному краевому случаю.
4. После каждого зелёного шага делать небольшой содержательный коммит.
5. Не передавать в общую ветку состояние с падающими тестами.
6. Если после изменения одновременно появились несколько возможных причин
   ошибки, откатывать только последний маленький шаг и дробить его.
7. Для ML-пайплайнов дополнительно фиксировать не только unit-тесты, но и
   воспроизводимые метрики, конфигурацию и контрольный набор примеров.

При работе с агентом это можно превратить в явный протокол:

```text
Выполни только одно правило спецификации.
Сначала добавь тест и покажи ожидаемое красное состояние.
Затем внеси минимальное изменение реализации.
Запусти все связанные тесты.
Не переходи к следующему правилу до зелёного состояния.
Покажи diff перед коммитом.
```

Такой режим уменьшает объём контекста, который нужно одновременно удерживать
человеку и агенту, а каждый результат остаётся проверяемым и обратимым.

## 6. Итоговый вывод

Практика показала, что маленький шаг определяется не количеством строк, а
числом одновременно вводимых предположений. В первой задаче один тест содержал
сразу четыре предположения, поэтому исправление получилось сравнительно крупным.
Во второй задаче правила вводились отдельно, и ошибка на границе была сведена к
одному оператору.

Полезная рабочая схема выглядит так:

```text
зелёная точка → одно новое правило → красный тест → минимальный код →
все тесты зелёные → коммит → инспекция размера шага
```

Если причина падения теста перестаёт быть очевидной, значит, шаг уже оказался
слишком большим.
Непосредственно на работе и при реализации сайд-проекта коммиты формирую по мере завершения некой целостной, логически связанной задачи, например блок методов схожего функционала.
Уже сейчас ловлю себя на мысли, что не запускаю тесты при мельчайших изменениях, только при крупных и уж никак не откатываю код к последнему коммиту, когда все тесты были зелеными.
Теперь практика точно изменится в лучшую сторону.
