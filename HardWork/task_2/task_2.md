# Работа с Atheris

**Репозиторий с fuzz-тестами:**
[TaxiTracker / fuzz](https://github.com/Voldek404/TaxiTracker/tree/main/TaxiTracker/fuzz)

## Вводные

1. Дипломный проект.
2. Количество строк Python-кода — **6822**.

Для применения fuzz-тестирования было выбрано несколько `view` в связке с соответствующими сериализаторами:

1. `VehiclesDetailApiView`
2. `VehiclesApiView`
3. `VehicleTrackAPIView`

Для данных `view` я подготовил **4 отдельных файла fuzz-тестирования** и запускал их отдельно, чтобы получать разделенные результаты и логи для каждого тестируемого API.

Тестировались методы **GET, POST и PATCH** с целью проверки наличия сбоев, вызванных необработанными исключениями, некорректной обработкой входных данных и проблемами в архитектуре приложения.

## Выявленные баги

### 1. Возможность записи отрицательных значений в числовые поля модели

Для `int`-полей моделей были установлены ограничения только по верхней границе допустимых значений. В результате API позволял, например, успешно создать объект с отрицательной ценой, возвращая `201 Created`.

Данное обстоятельство было устранено на уровне сериализатора, отвечающего за валидацию данных перед записью в БД.

### 2. Возможность запроса точек поездок без указания ID автомобиля

При отсутствии `vehicle_id` запрос автоматически приводил к получению всех точек поездок доступного пользователю автопарка за заданный временной промежуток. Помимо некорректного поведения API, это приводило к очень долгому выполнению запроса.

Была добавлена обработка отсутствующего `vehicle_id`, а также `select_related` для дополнительного ускорения запроса на основании ранее проведенных в рамках дипломного проекта работ по оптимизации запросов.

До устранения данного бага к концу запущенного процесса fuzz-тестирования потребление памяти доходило примерно до **2 ГБ**.

### 3. Возможность передачи строкового ID автомобиля

После устранения бага №2 автоматически выявилась проблема с возможностью передать строковое значение в качестве ID автомобиля.

После добавления проверки обязательного наличия `vehicle_id` fuzz-тестирование позволило выявить следующий уровень проблемы — отсутствие корректной обработки типа переданного идентификатора.

Данная проблема также была исправлена.

### 4. Невалидное поле сериализатора, отсутствующее в соответствующей модели

Поле `trip` отсутствовало в модели, однако сериализатор обращался к нему. При определенных структурах запроса Atheris позволял дойти до данной ветки сериализации, после чего возникало необработанное исключение.

Проблема была выявлена и устранена.

### 5. Некорректное получение значения `trip_id`

Также было выявлено некорректное обращение:

```python
"trip_id": instance.trip_id
```

У объекта `VehicleTrackPoint`, передаваемого в `instance`, отсутствовал соответствующий атрибут `trip_id`, вследствие чего при достижении данной ветки сериализации запрос завершался необработанным `AttributeError`.

Логика получения `trip_id` была исправлена.

## Итоги

При работе с генерацией данных для fuzz-тестирования для себя выделил, что для API эффективно отдельно мутировать каждое поле, задавая максимально разнообразные значения, включая различные типы данных и граничные значения.

При этом важно сохранять остальные части запроса валидными. В противном случае запрос зачастую отбрасывается сериализатором с `400 Bad Request`, и fuzz-тестирование фактически не доходит до более глубокой логики приложения.

После проверки отдельных полей можно переходить к их совместным мутациям и проверять взаимодействие нескольких некорректных или граничных значений.

Я бы даже сказал, что внимательный подход к генерации входных данных — один из ключей к успешному fuzz-тестированию. Сам по себе большой объем случайных данных не гарантирует качественной проверки: важно добиться того, чтобы генерируемые значения позволяли проходить разные ветки приложения.

В одном из запусков Atheris было выполнено более **36 000 итераций** со скоростью около **120 запросов в секунду**. В процессе тестирования удалось обнаружить несколько ошибок, которые не были выявлены обычными функциональными тестами.
