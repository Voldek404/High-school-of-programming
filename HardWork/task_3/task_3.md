## 1. Итог и границы работы

Явно определены правила повторов, знака мощности, порогов сигнализации и ошибок хранилища.

Недостоверные измерения не прерывают обработку: они сохраняются с `reasons`, а расчёты возвращают частичный результат или неизвестное решение. 
Цвет относится к интерфейсу пользователя: модель предоставляет качество и причину, но сама ничего не рисует.

Вход - получасовая **средняя мощность**, полученная из программного комплекса. `energy_kwh()` вычисляет энергию по этим мощностям.

Фраза «один код — один дизайн» применена практически: у каждого публичного метода указан один предметный смысл, единицы, условия и последствия. Математическая уникальность дизайна и формальная корректность не доказаны. Тесты проверяют выбранные свойства, но не заменяют доказательство для всех входов.

## 2. Логическая спецификация — источник правил

### Измерение `HalfHour` получасовки

- Ключ: `(meter_number, start UTC, channel)`. Номер прибора связывает его измерения; значение мощности частью ключа не является.
- `start` — начало интервала продолжительностью 30 минут. Отчётная сетка явно определена в UTC: минуты 00 или 30, секунды и микросекунды равны нулю.
- `average_kw` — средняя активная мощность за этот интервал, кВт. Отрицательные значения допустимы и сохраняют направление.
- Номер прибора и канал — непустые строки. Время содержит часовой пояс. Нарушение этих требований — ошибка использования API (`ValueError`), поскольку запись нельзя корректно идентифицировать.
- Отсутствующая/нечисловая/неконечная мощность преобразуется в `None` и маркируется. Смещённый timestamp сохраняется точно, но делает измерение недостоверным.
- Числовой вход: `numbers.Real`, кроме `bool`, представимый конечным `float`. Строки и `Decimal` требуют явного преобразования на границе загрузки.
- `reasons` — кортеж непустых строк. Причины дедуплицируются и сортируются; порядок перечисления причин не несёт смысла.
- Инвариант: `is_reliable` истинно тогда и только тогда, когда причин нет. Объект неизменяем.

Сетка UTC — выбранное ограничение этого примера. Если комплекс использует другую сетку, это изменение спецификации и адаптера загрузки, а не повод незаметно ослаблять тесты.

### Расчёт энергии `EnergyCalculator.energy_kwh()`

Предусловия: передан непустой по длительности `ReportPeriod`; его границы лежат на получасовой сетке. Все входные записи относятся к одному прибору и каналу, включая записи за пределами периода.

Период полуоткрытый: `[start, end)`. Запись ровно на `end` относится к следующему отчёту.

Для каждой ожидаемой получасовки обработаны следующие edge cases:

1. Нет записи — интервал не учтён.
2. Несколько одинаковых нормализованных записей — учитывается одна.
3. Различаются мощность или качество записей одного ключа — ни одна не учитывается; возвращается причина конфликта.
4. Единственная запись недостоверна — не учитывается, причины сохраняются.
5. Единственная запись достоверна — учитывается `Pср × 0.5 часа`.

Постусловия:

```text
energy_kwh = сумма(Pср × 0.5) по учтённым интервалам
expected_intervals = (end - start) / 30 минут
counted_intervals = число учтённых уникальных получасовок
is_complete ⇔ все ожидаемые интервалы учтены и сумма конечна
```

При отсутствии данных сумма равна нулю, но отчёт неполон. Частичная сумма не выдаётся за полную энергию периода. При числовом переполнении возвращается `energy_kwh=None` с причиной. Перестановка входных записей не меняет результат. Исходные записи не изменяются.

### Коэффициент мощности и сигналы

 Методы и Гарантированный смысл 
 `signed_power_factor(P, S)` | Знаковый `P/S` при конечных `S > 0` и `abs(P) <= S`; иначе `None`. Результат в `[-1, 1]`. 
 `power_exceeded(interval, limit)` | Для достоверной получасовки сигнал при `Pср > limit`. Равенство допустимо. Отрицательное направление не проверяется по модулю. 
 `low_voltage_phases(values, nominal)` | По каждой A/B/C сигнал при `U < Uном × 0.70`: снижение строго более 30%. 

`P/S` не объявлен универсальным `cos(phi)`: при несинусоидальности это разные характеристики. Знак реактивной мощности и соглашение конкретного прибора этот метод не определяет. Чтобы реализовать именно рабочий косинус, требуется согласовать его формулу и знаковую конвенцию с данными комплекса.

Ненадёжная мощность даёт `CheckResult(triggered=None, reasons=...)`, а не `False`. Неизвестное решение отличается от отсутствия превышения. Превышение лимита само по себе не делает измерение недостоверным.

Плохая/отсутствующая/отрицательная величина напряжения относится к `unknown_phases`. Известные фазы проверяются независимо. Метод оценивает переданные значения; длительность провала он не определяет.

Некорректный лимит или номинал — ошибка конфигурации (`ValueError`), а не недостоверность измерения.

### Хранилище `MeterRepository`

Абстрактный класс задаёт контракт, независимый от SQL. Реализации: `SQLiteMeterRepository` и `InMemoryMeterRepository`.

| Операция / случай | Постусловие |
| `add_meter(number)` | Прибор зарегистрирован; повторная регистрация безопасна. |
| `save()` для нового ключа | Сохранено измерение вместе с качеством, включая недостоверные данные. |
| `save()` для точного повтора | Хранилище не изменилось; повтор не создаётся. |
| `save()` для конфликтующего ключа | `ConflictingIntervalError`; старая запись не перезаписана. |
| Прибор не зарегистрирован | `UnknownMeterError`; ничего не записано. |
| `list_for_meter(number)` | Новый список неизменяемых измерений, сортировка `(start, channel)`. Для неизвестного прибора — пустой список. |
| Ошибка backend | `StorageError`; исходная техническая причина сохранена в `__cause__`. |

Таким образом, **недостоверные значения сохраняются**, а невозможность адресовать или однозначно записать измерение описывается отдельной ошибкой. Массовый загрузчик при необходимости перехватывает доменные ошибки по записи; в этом примере загрузчик не реализован.

Контракт рассчитан на последовательные вызовы. Для SQLite соединением владеет вызывающий код; репозиторий не закрывает его. Каждая запись использует свою транзакцию. Вызов внутри внешней активной транзакции запрещён, чтобы репозиторий не закоммитил чужую работу. Проверка и запись интервала выполняются внутри `BEGIN IMMEDIATE`.

## 3. Примеры исправленного кода после прочтения СИ


### 3.1. От неявного смысла полноты к явному отчётному периоду


**До — проблема на уровне дизайна.** Метод принимал только записи. Не было определено, относительно какого периода результат должен считаться полным. Реализация проверяла непрерывность имеющихся данных:

```python
unique_times = sorted(seen)
if any(b - a != 1800 for a, b in zip(unique_times, unique_times[1:])):
    reasons.append('Есть пропуск или смещение интервалов')
return EnergyResult(total, not reasons, reasons)
```

Этот код мог корректно проверять промежутки между записями, но не мог гарантировать полноту за требуемый час. Например, единственная запись в 12:00 с мощностью 4 кВт давала `2 кВт·ч, is_complete=True`. Для отчёта 12:00–13:00 этого недостаточно: нет получасовки 12:30.

**После — сначала определена гарантия.**

> Метод рассчитывает энергию за явно заданный период `[start, end)`. Результат полный только тогда, когда учтены все ожидаемые получасовки этого периода и сумма конечна.

Гарантия стала частью публичного интерфейса:

```python
def energy_kwh(intervals: Iterable[HalfHour], period: ReportPeriod) -> EnergyResult:
    ...
```

Из неё следует проверка в реализации:

```python
expected, counted = period.interval_count, len(powers)
if counted != expected:
    reasons.add(MISSING_INTERVALS)
```

Вместе с остальными правилами метода — учётом только достоверных, уникальных интервалов на получасовой сетке — это обнаруживает пропуски и в середине, и на краях периода. Само сравнение двух чисел отдельно от этих правил ещё не гарантировало бы полноту.

Тот же пример теперь даёт `2 кВт·ч, is_complete=False, expected_intervals=2, counted_intervals=1`.

**Проверка следует спецификации:** `test_missing_beginning_middle_or_end_is_detected` проверяет три положения пропуска. Он проверяет полноту периода, а не наличие конкретного `if`.

**Что применено из статьи:** уточнён смысл результата и расширен контракт метода; затем из контракта получены код и тесты. Это изменение дизайна, выраженное в реализации.

### 3.2. От случайного выбора первой записи к заданной политике конфликтов

«Код не должен следовать тестам, ни тесты не должны следовать коду. И тесты, и код должны следовать дизайну, логической архитектуре».

**До — предметное решение было спрятано в алгоритме.** При повторном timestamp учитывалась первая запись:

```python
if timestamp in seen:
    reasons.append('Повтор получасовки: требуется разрешение конфликта')
    continue
```

Тем самым порядок загрузки фактически определял, какую мощность считать истинной. Для двух версий одной получасовки, 4 и 9 кВт, получалось либо 2, либо 4.5 кВт·ч. Правило «первая запись достовернее» не было обосновано предметными требованиями.

**После — политика определена независимо от алгоритма.**

> Точные повторы учитываются один раз. Если записи одного ключа различаются мощностью или качеством, весь конфликтующий интервал исключается из расчёта с указанием причины. Перестановка входных записей не меняет результат.


Текущая реализация выбранного правила:

```python
variants = set(groups[start])
if len(variants) > 1:
    reasons.add(CONFLICTING_INTERVALS)
    continue
```

Для конфликтующих 4/9 кВт и следующей достоверной получасовки 6 кВт сумма составляет 3 кВт·ч при любом порядке; отчёт неполон.

**Проверки следуют спецификации:** `test_conflict_is_excluded_independently_of_input_order` проверяет перестановки, а `test_exact_repeat_is_idempotent` — повторное предъявление одинаковой записи. Тесты не требуют применения `set`: другой алгоритм может соблюдать тот же контракт.

Неявная зависимость от порядка заменена явным предметным правилом. И код, и тесты подчинены этому правилу.

### 3.3. От выбранного SQL-типа к гарантии сохранения идентичности измерения

Компонент должен быть корректен по спецификации и допускать замену реализации «с сохранением требований спецификации».

**До — представление данных нарушало смысл ключа.** Временная часть ключа записывалась как целое число секунд:

```python
int(interval.start.timestamp())
```

Интервалы 12:00:00.000001 и 12:00:00.000002 превращались в один ключ. Вторая запись вызывала `sqlite3.IntegrityError`; первая читалась уже как 12:00:00. Хранилище меняло идентичность и исходное время измерения.

**После — гарантия сформулирована в терминах измерений.**

> Ключ измерения — `(номер прибора, точное начало UTC, канал)`. Сохранение и чтение не меняют этот ключ. Разные моменты времени остаются разными; один момент, представленный в разных часовых поясах, остаётся одним моментом.

Для SQLite эта гарантия реализована так:

```python
start = interval.start.isoformat(timespec='microseconds')
```

UTC-нормализация выполняется в `HalfHour`. ISO-строка — деталь SQLite adapter, а не требование к любому хранилищу. Другая реализация вправе хранить время иначе, сохраняя точность ключа.

Оба смещённых измерения теперь сохраняются раздельно и остаются недостоверными: хранилище не превращает их в корректные получасовки округлением времени.

**Проверка следует спецификации:** `test_distinct_subsecond_times_are_preserved_even_if_unreliable` выполняется для SQLite и памяти; `test_timezone_equivalence_is_also_idempotent_in_storage` проверяет эквивалентные часовые пояса.

Явно определена гарантия хранилища и устранена зависимость клиента от формата хранения. Сам переход с `int` на строку — исправление реализации под эту гарантию, а не отдельная архитектура.

### 3.4. От повторного толкования `None` к сохранению качества измерения

Нужно описывать, **что** компонент гарантирует во всей системе, а не только **как** он работает; спецификация задаёт пред- и постусловия операций.

 До применения рекомендаций`NaN` преобразовывался в `None` с причиной «Мощность не является конечным числом». После чтения конструктор повторно трактовал `None` как отсутствие измерения:

```python
if value is None:
    reasons.append('Нет данных от прибора')
```

В результате `restored != original`: сохранение и чтение добавляли новую причину недостоверности. БД сохраняла числовое поле, но система не сохраняла смысл качества целиком.

После — определено постусловие успешного сохранения и чтения.

> Для нормализованного измерения `x`, после успешного сохранения чтение возвращает равное ему измерение: сохраняются ключ, мощность и причины качества. Хранение не переоценивает измерение.

Для нормализации отдельно задано свойство:

> Повторная нормализация уже нормализованной записи не меняет её.

Реализация учитывает причину ранее выполненного преобразования:

```python
if value is None:
    if INVALID_POWER not in reasons:
        reasons.add(MISSING_POWER)
```

Непригодное числовое значение и отсутствующее измерение остаются различимыми по причинам. Это свойство относится к нормализованному объекту: исходный `NaN` как сырой вход в числовой колонке не сохраняется.

**Проверка следует спецификации:** `test_unreliable_interval_roundtrips_and_does_not_block_next_one` сравнивает весь объект до и после хранения и проверяет сохранение следующего достоверного интервала.

Общее обещание «хранить измерение с качеством» уточнено до проверяемого постусловия. Условная ветка исправлена как следствие этого контракта.

### 3.5. От SQLite-специфичного интерфейса к заменяемому хранилищу

«Логический уровень подразумевает максимально “модульное” взаимодействие между компонентами вашего проекта»; реализация компонента может быть заменена при сохранении спецификации.

До — клиент зависел от технического исключения SQLite.

```python
with pytest.raises(sqlite3.IntegrityError):
    repository.save(sample())
```

Внешнее поведение определялось ограничением SQL. Интерфейс не разделял точный повтор, конфликтующие версии и неизвестный прибор. Тест закреплял особенность выбранного backend.

После — определён предметный контракт.

> Точный повтор безопасен. Конфликтующая запись вызывает `ConflictingIntervalError` без перезаписи. Неизвестный прибор вызывает `UnknownMeterError` без записи. Техническая ошибка хранения представляется как `StorageError`.

Этот контракт объявлен в абстрактном классе:

```python
class MeterRepository(ABC):
    @abstractmethod
    def save(self, interval: HalfHour) -> None:
        pass
```

`SQLiteMeterRepository` и `InMemoryMeterRepository` реализуют его. Само наследование не гарантирует соответствие: смысл гарантий задан документацией, а наблюдаемые исходы проверены общими тестами.

Пример контрактной проверки, после предварительного сохранения `sample()`:

```python
with pytest.raises(ConflictingIntervalError):
    repository.save(sample(9))
repository.save(sample(6, 30))
assert repository.list_for_meter('001') == [sample(), sample(6, 30)]
```

Тест проверяет отказ от перезаписи и возможность следующей корректной записи. Он запускается на обеих реализациях без изменения ожиданий.

Контракт клиента выражен в терминах предметной области, реализации скрыты за ним, тесты проверяют общий контракт. Это прямое изменение модульной архитектуры. Прохождение тестов подтверждает заменяемость в проверенных сценариях, но не является формальным доказательством.

### 3.6. От безымянных чисел к видимым предметным понятиям

«Делайте дизайн по возможности явно видимым в коде»; пример статьи — замена числа `65` на `RETIREMENT_AGE`.

До — формулы не называли используемые правила. Фрагменты из двух методов:

```python
total += row.average_kw * 0.5
```

```python
elif value < nominal_v * 0.7:
    low.append(phase)
```

По одним числам нельзя установить, почему используются именно эти коэффициенты и какие требования должны сохраниться при изменении кода.

После — сначала указан предметный смысл.

> Входная мощность усреднена за 30 минут; вклад в энергию равен мощности, умноженной на 0.5 часа. Сигнал по напряжению возникает при снижении строго более 30% от номинала; ровно 30% сигнал не вызывает.

Понятия отражены в именах:

```python
HALF_HOUR_HOURS = 0.5
VOLTAGE_DROP_FRACTION = 0.30
```

Фрагменты реализации:

```python
fsum(p * HALF_HOUR_HOURS for p in powers)
```

```python
threshold = float(nominal_v) * (1 - VOLTAGE_DROP_FRACTION)
```

**Проверки следуют спецификации:** `test_energy_is_half_the_sum_of_half_hour_average_powers` проверяет единицы и расчёт; `test_voltage_drop_is_strictly_more_than_thirty_percent` — значения на пороге и по обе стороны от него.

Предметные понятия явно обозначены в коде и связаны с документированными правилами. Переименование констант само по себе не создаёт полноценной спецификации; гарантия появляется из сочетания смысла, контракта и реализации. Применение `fsum` — отдельная деталь вычисления, не доказательство улучшения дизайна.

## 4. Разделение трёх уровней и характер изменений

**Соответствие статье:** «Рассуждения о программе на разных уровнях смешивать нельзя».

На примере конфликтующих получасовок:

| Уровень | Рассуждение | Что позволяет утверждать |
| --- | --- | --- |
| Спецификация | Для любого допустимого набора записей конфликтующий ключ не участвует в сумме; перестановка записей не меняет результат. | Какое поведение требуется от любой реализации метода. |
| Реализация | Записи сгруппированы по времени; одинаковые варианты схлопываются; группа с несколькими вариантами исключается. | Как текущий алгоритм обеспечивает выбранное правило; это требует рассуждения о коде, а не только запуска. |
| Исполнение | Для конкретных записей 4/9/6 кВт и проверенных перестановок получено 3 кВт·ч. | Что произошло в этих запусках. Это не доказывает свойство для всех входов. |

Архитектурные решения и исправления кода в этом пересмотре имеют разный характер:

| Пример | Изменение на уровне спецификации / дизайна | Следствие в реализации |
| --- | --- | --- |
| 3.1 | Полнота определяется относительно явно заданного периода. | Добавлен `ReportPeriod`; проверяются ожидаемые интервалы. |
| 3.2 | Определены точные повторы, конфликты и независимость от порядка входа. | Варианты одного ключа сравниваются до учёта мощности. |
| 3.3 | Явно задана сохранность точного ключа при хранении. | Убрано усечение времени до целых секунд. |
| 3.4 | Сохранность качества уточнена до равенства нормализованного объекта после чтения. | Повторная нормализация не добавляет ложную причину. |
| 3.5 | Введён независимый от SQL контракт с предметными исходами. | Абстрактный репозиторий, две реализации, преобразование технических ошибок. |
| 3.6 | Явно обозначены единицы и смысл порогов. | Семантические имена констант; формулы используют эти понятия. |
